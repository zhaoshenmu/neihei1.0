# ⚙️ 内核架构（Kernel Engine）

> ⚠️ **铁律：内核只做三件事** ———— 查记忆、验幻觉、写回
>
> 任何想往内核里塞「第四件事」的行为，都必须先审视这个文档。
> 如果你发现自己正在往内核里加「提示词管理」「模型调用」「格式渲染」「数据导出」
> 或其他不属于三原则的功能————停下来，把它放到外面。

---

## 一、三原则（核心铁律）

### 原则 1：查记忆（防失忆）

```
输入到达内核 →
  查 Layer 0（全部强制注入）
  查 Layer 1（按相关性取 Top-20）
  查 Layer 2（按相关性取 Top-10，仅供参考）
  忽略 Layer 3
→ 用记忆增强输入 → 输出到下一步
```

**边界**：内核只负责「检索记忆 + 注入上下文」，不负责「编辑记忆的内容」。编辑记忆是用户在 KernelPanel 的 MemoryTab 中手动做的事。

### 原则 2：验幻觉（防幻觉）

```
LLM 输出到达内核 →
  提取三元组
  与 Layer 0-1 对比
  检测矛盾/不一致/逻辑断裂
  决策：放行 / 标记 / 打回
→ 输出验证结果
```

**边界**：内核只负责「检测冲突」，不负责「修改 LLM 输出」。修改输出是 Edit 节点或用户手动做的事。

### 原则 3：写回（持续学习）

```
验证通过的 LLM 输出 →
  新三元组写入 Layer 2（待确认）
  用户确认 → 升 Layer 0-1
  旧数据降级/遗忘
→ 同步到画布图谱层
```

**边界**：内核只负责「写入临时记忆 + 执行降级策略」，不负责「永久存储」。持久化由外部的存储层（localStorage / IndexedDB）负责。

---

### 违反三原则的警示信号

如果你发现自己在做以下任何一件事，说明你**正在破坏三原则**：

| 🚨 警示行为 | 违反了哪条 | 正确做法 |
|------------|-----------|---------|
| 在内核里写提示词模板编辑器 | 三原则之外 | 放到 `chajian/prompts/` 或 Edit 节点 |
| 在内核里调用 LLM | 三原则之外 | 放到 🤖 LLM 节点 |
| 在内核里渲染图谱 | 三原则之外 | 放到 📦 Output 节点 + GraphVisualizer 插件 |
| 在内核里导出文件 | 三原则之外 | 放到 📦 Output 节点的 export 函数 |
| 在内核里做格式转换（文本→JSON） | 三原则之外 | 放到专门的数据转换节点 |
| 在内核里做持久化/加载 | 三原则之外 | 放到独立的 Store / Storage 层 |
| 给内核增加新的输入/输出端口 | 可能是扩展 | 先问：这是「查记忆」「验幻觉」「写回」的哪一步？ |
| 在内核面板加新标签 | 可能是扩展 | 先问：这个标签的功能属于三原则吗？不是就外移 |

## 二、内核的纯净边界（架构师经验）

### 内核包含什么（只能有这些）

```
src/kernel/
├── engines/           # 三个引擎，对应三原则
│   ├── MemoryEngine.ts
│   ├── ConstraintEngine.ts
│   └── ValidationEngine.ts
├── layers/            # 洋葱层管理，对应「查记忆」和「写回」
│   ├── OnionLayerManager.ts
│   ├── MemoryConsolidator.ts
│   └── ConflictDetector.ts
├── tabs/              # 面板标签——严格遵循三原则，只有4个
│   ├── MemoryTab.tsx       # 【查记忆】展示4层记忆
│   ├── ConstraintsTab.tsx  # 【查记忆】展示当前约束（来自JSON模板）
│   ├── DetectionTab.tsx    # 【验幻觉】展示检测日志
│   └── SettingsTab.tsx     # 内核自身设置
│   # ❌ 不包含"图谱扩展"标签——图谱由插件节点提供，非内核职责
│   # ❌ 不包含"执行控制"标签——LLM调用/进度管理由外部编排层负责
├── KernelNode.tsx     # 画布节点，只有输入/输出端口
├── KernelPanel.tsx    # 双击面板，只展示上述4个标签（标签5、6由插件挂载）
├── kernel.store.ts    # 内核状态
└── kernel.types.ts    # 类型定义
```

### 内核不包含什么（这些要放到外面）

| 功能 | 归属 | 理由 |
|------|------|------|
| 提示词模板 JSON 管理 | `chajian/prompts/*.json` | 策略配置，不是内核逻辑 |
| LLM 调用 | 🤖 LLM 节点 | 模型调用是独立能力 |
| 输出格式渲染 | 📦 Output 节点 + 插件 | 渲染不属于记忆/验证/写回 |
| 文件导出 | 📦 Output 插件的 export | 持久化在外层 |
| 工作流调度 | `src/dataflow/WorkflowEngine.ts` | 流程编排不是内核职责 |
| 用户认证/设置 | `src/store/` | 属于应用层 |

## 三、策略层设计（关于动态提示词 JSON 的架构决策）

### 架构师经验：提示词模板是「配置」，不是「代码」

```
❌ 错误做法：把提示词模板写在内核代码里
   改一行提示词 → 改代码 → build → 部署
   PM 一天改 5 次 → 开发者成为瓶颈

✅ 正确做法：提示词模板是 JSON 配置文件
   改 JSON → 保存即生效 → 无需重启
   PM 自己改 → 开发者只需要定义 JSON schema
```

### 最终方案：三明治架构

```
┌────────────────────────────────────────────────────────────┐
│  策略层 (chajian/prompts/*.json)                           │
│  ─── 纯JSON，用户可直接编辑                                 │
│  ─── 模板 + 变量定义 + 注入规则                             │
│  ─── 多版本、多环境、多项目                                 │
│  ─── 放新JSON文件 = 自动注册新模板                          │
├────────────────────────────────────────────────────────────┤
│  内核引擎 (ConstraintEngine.ts)                             │
│  ─── 读JSON → 解析模板 → 填充变量 → 注入Layer 0-1         │
│  ─── 不关心模板内容，只关心执行                             │
│  ─── 换模板 = 换JSON文件，内核不动                          │
├────────────────────────────────────────────────────────────┤
│  执行层 (🤖 LLM 节点)                                      │
│  ─── 接收已构建好的完整提示词                              │
│  ─── 只管生成，不关心提示词怎么来的                        │
└────────────────────────────────────────────────────────────┘
```

## 四、内核双重身份

内核同时存在于两个层面：

| 层面 | 身份 | 说明 |
|------|------|------|
| **画布上** | ⚙️ Kernel 节点 | 工作流中的可视化节点，有输入/输出端口 |
| **内存中** | Kernel Engine | 后台运行的引擎，管理记忆和验证 |

```
画布上的 Kernel 节点               内存中的 Kernel Engine
┌─────────────────────┐           ┌─────────────────────────┐
│ ⚙️ Kernel           │           │  MemoryEngine            │
│                     │   驱动    │  ├─ OnionLayerManager    │
│ 输入: ● text_in     │──────────►│  ├─ MemoryConsolidator  │
│       ● triples_in  │           │  └─ ConflictDetector    │
│ 输出: ● text_out    │           │                         │
│       ● validated   │           │  ConstraintEngine        │
│                     │           │  ├─ ContextBuilder       │
│ 双击打开控制面板     │           │  └─ Injector            │
│ ┌─────────────────┐ │           │                         │
│ │ 记忆层 | 约束    │ │           │  ValidationEngine        │
│ │ 检测 | 设置     │ │           │  ├─ TripleExtractor     │
│ └─────────────────┘ │           │  ├─ ConflictChecker     │
└─────────────────────┘           │  └─ DecisionMaker       │
                                  └─────────────────────────┘
```

## 五、记忆洋葱层（Onion Layer）

### 5.1 五层结构

| 层 | 名称 | 说明 | 置信度阈值 | 来源 | 保留策略 |
|----|------|------|-----------|------|---------|
| 🧅 **Layer 0** | **核心事实（大纲设定）** | 用户手写/确认的不可变更事实 | ≥ 0.95 | 用户手动确认 | **永不遗忘** |
| 🧅 **Layer 1** | **故事骨架（精炼后转折点）** | 多源交叉验证 + 精炼节点输出的核心转折 | ≥ 0.70 | 多章交叉验证 + 精炼 | **永不遗忘** |
| 🧅 **Layer 2** | **近期详情** | 最近N章的完整细节，窗口外降级 | ≥ 0.40 | LLM 输出提取 | 窗口外自动降级 |
| 🧅 **Layer 3** | **末梢细节** | 很久以前的日常/环境/对话细节 | < 0.40 | LLM 单次输出 | **优先遗忘** |
| 🧅 **Layer 4** | **索引层** | 只存"去哪查"，不存内容 | - | 降级后写入 | 不占活跃内存 |

### 5.2 层级规则

```
Layer 0: 大纲设定（永不遗忘）
├── 用户手动标注「确认」的三元组
├── 不可被 LLM 覆盖或修改
├── 每次 LLM 调用强制注入
└── 示例：林夜是男主角、故事背景是修仙世界

Layer 1: 故事骨架（永不遗忘）
├── 从 🦴 Refine 精炼节点输出的关键转折点
├── 每卷精炼后写入，只保留决定性剧情
├── 注入 LLM 上下文（优先于所有下层）
└── 示例：(林夜, 第一卷结局, 筑基成功)

Layer 2: 近期详情（窗口内保留）
├── 最近 N 章的完整三元组细节
├── 窗口可配置（默认保留最近 7 章）
├── 超出窗口 → 开始进入 Layer 3 待遗忘队列
└── 示例：(林夜, 第12章, 与慕容雪在青城山相遇)

Layer 3: 末梢细节（优先遗忘）
├── 窗口外很久以前的日常描写/对话
├── 引用计数 < 阈值时优先清理
├── 不进入 LLM prompt
└── 示例：(林夜, 第3章, 穿蓝色衣服)

Layer 4: 索引层（不占活跃内存）
├── 被遗忘的三元组留下索引："去 Storage 查第3章"
├── 需要时可通过索引恢复详情
├── 不占用 LLM prompt token
└── 示例：(林夜, 第3章, [storage:chapter_3])
```

### 5.3 升降级流程

```
               用户确认
Layer 2 ──────────────► Layer 0
  │                        │
  │ 超出时间窗口            │ 永不降级
  ▼                        ▼
Layer 3 (待遗忘)       Layer 0 (保留)

               精炼节点输出
校对后全文 ───────────► Layer 1 (骨架)
                                │
                                │ 永不降级
                                ▼
                           Layer 1 (保留)

               引用计数 < 阈值
Layer 3 ──────────────► Layer 4 (索引)
                                │
                                │ 需要时去 Storage 查
                                ▼
                           恢复详情
```

## 六、约束闸门（Constraint Engine）

### 6.1 约束来源与注入时机

**约束来源**：约束来自 📋 Outline 节点（结构化大纲模板）的【世界观】【人物】【主线】【红线规则】四个板块。这些内容**不入内核洋葱层**，不参与遗忘机制，每次 LLM 调用时从 Outline 节点直接读取并注入。

```
📋 Outline 节点
    ├── 【世界观】 → 强制注入（不入洋葱层）
    ├── 【人物】   → 强制注入（不入洋葱层）
    ├── 【红线规则】→ 最高优先级注入（不入洋葱层）
    └── 【主线】   → 参考注入（不入洋葱层）
```

**关键原则**：换项目只需换 Outline 节点的配置文件，内核干净无污染。

约束在 LLM 调用前注入，确保 LLM 不会忘记关键事实：

```
用户想法 → Kernel → [约束注入] → 增强提示词 → LLM
                         │
                         ├── Layer 0 全部注入（不可违反）
                         ├── Layer 1 按相关性注入
                         ├── 当前章节摘要
                         ├── 角色设定
                         ├── 世界设定
                         └── 风格指令
```

### 6.2 约束类型

| 约束类型 | 说明 | 示例 |
|---------|------|------|
| **角色约束** | 角色基本信息、性格、能力 | 林夜：男主，性格坚毅，拥有青冥剑 |
| **世界约束** | 世界观设定 | 修仙世界，有炼气/筑基/金丹境界 |
| **情节约束** | 当前故事进展 | 当前第5章，林夜刚发现家族秘辛 |
| **风格约束** | 文风、节奏控制 | 玄幻风格，热血，节奏明快 |
| **逻辑约束** | 不可违反的物理/逻辑规则 | 死人不能复活（除非设定有复活能力） |

### 6.3 约束格式

```typescript
interface Constraint {
  type: 'character' | 'world' | 'plot' | 'style' | 'logic';
  content: string;
  layer: 0 | 1;          // 约束的来源层
  isRequired: boolean;    // true=必须遵守, false=仅供参考
}

// 注入到 LLM 时的格式
const injectedPrompt = `
[系统约束 - 不可违反]
${constraints.filter(c => c.isRequired).map(c => `- ${c.content}`).join('\n')}

[上下文参考]
${constraints.filter(c => !c.isRequired).map(c => `- ${c.content}`).join('\n')}

[用户任务]
${userInput}
`;
```

## 七、幻觉检测管道（Validation Engine）

### 7.1 检测流程

```
LLM 输出 → ──────────────────────────────────────────────┐
                                                          │
  ① 三元组提取                                             │
     ├ 从 LLM 输出中提取所有 (主体, 谓词, 客体)            │
     └ 示例："林夜拔出青冥剑" → (林夜, 拥有, 青冥剑)       │
                                                          │
  ② 冲突对比                                               │
     ├ 与 Layer 0-1 逐条对比                               │
     ├ 检测矛盾（例如林夜同时位于两个不同地点）             │
     ├ 检测不一致（例如青冥剑之前已丢失却又出现）           │
     └ 检测逻辑断裂（例如角色做出与性格不符的行为）         │
                                                          │
  ③ 决策                                                   │
     ├ 无冲突 → 放行，新三元组写入 Layer 2                 │
     ├ 轻微冲突 → 标记冲突，询问用户                       │
     └ 严重冲突 → 打回 LLM 重写，日志告警                  │
                                                          │
  ④ 记忆更新                                               │
     ├ 新三元组写入 Layer 2（待确认）                      │
     ├ 用户手动确认 → 提升到 Layer 0-1                    │
     └ 旧数据 → 执行 MemoryConsolidator                   │
                                                          │
输出 → 下一节点
```

### 7.2 矛盾类型

| 矛盾类型 | 严重程度 | 示例 | 处理方式 |
|---------|---------|------|---------|
| **事实矛盾** | 🔴 严重 | 林夜同时位于"江城"和"青城山" | 打回LLM重写 |
| **关系矛盾** | 🟡 中等 | 林夜拥有青冥剑 vs 林夜失去青冥剑(无事件) | 询问用户 |
| **性格矛盾** | 🟡 中等 | 坚毅的林夜突然懦弱退缩 | 标记冲突 |
| **逻辑断裂** | 🟢 轻微 | 角色知道了他不可能知道的信息 | 询问用户 |
| **设定违反** | 🔴 严重 | 炼气期修士打败元婴期 | 打回LLM重写 |

### 7.3 冲突检测算法

```typescript
function detectConflicts(newTriples: Triple[], layer0: Triple[], layer1: Triple[]) {
  const conflicts = [];

  // 对比 Layer 0（严重冲突）
  for (const nt of newTriples) {
    for (const lt of layer0) {
      if (nt.subject === lt.subject && nt.predicate === lt.predicate) {
        if (nt.object !== lt.object) {
          // 同一主体+谓词，但客体不同 = 矛盾
          conflicts.push({
            severity: 'critical',
            message: `${nt.subject} 的 "${nt.predicate}" 冲突：${lt.object} vs ${nt.object}`,
            source: lt,
            target: nt,
          });
        }
      }
    }
  }

  // 对比 Layer 1（中等冲突）
  // ... 相似逻辑，但 severity 为 'medium'

  return conflicts;
}
```

## 八、记忆压缩器（MemoryConsolidator）

### 8.1 压缩策略

```
每次新章节完成后触发：

Layer 0: 不压缩，永不遗忘
Layer 1: 不压缩，永不遗忘（精炼后的骨架永久保留）
Layer 2: 检查最后引用章节，超出时间窗口降级
Layer 3: 检查引用计数，低于阈值降级为索引
Layer 4: 不占活跃内存，需要时去 Storage 恢复
```

### 8.2 降级规则

| 条件 | 操作 |
|------|------|
| Layer 2 超出时间窗口（默认7章） | 降级为 Layer 3（待遗忘队列） |
| Layer 3 引用计数 < 3（超过20章未被查询） | 降级为 Layer 4（索引层） |
| Layer 4 索引数据 | 不占内存，需要时查 Storage |
| Layer 0 | **永不降级** |
| Layer 1（骨架精炼） | **永不降级** |

### 8.3 回溯机制

```typescript
interface MemorySnapshot {
  id: string;
  timestamp: number;
  chapterId: number;
  layer0: Triple[];

## 十一、内核边界红线与 EventBus 通信

### 11.1 内核的出口：只发事件，不推送

内核做完「写回」后，不直接调任何外部组件。只做一件事 —— **往 EventBus 发事件**：

```
⚙️ Kernel 的「写回」最后一步：
  MemoryConsolidator 完成降级
    → EventBus.emit('kernel:memory-updated', {
        version: 42,
        layers: { layer0: [...], layer1: [...], layer2: [...] },
        delta: { added: [...], removed: [...], upgraded: [...] }
      })
    → 结束（内核的事做完了）
```

谁订阅这个事件，内核不关心。

### 11.2 订阅者由外部组件自行注册

| 外部组件 | 订阅的事件 | 行为 |
|---------|-----------|------|
| 🕸️ Graph 节点 | `kernel:memory-updated` | 提取三元组 → 渲染图谱（只读） |
| 🗄️ Storage 节点 | `kernel:memory-updated` | 提取 Layer 0-2 → 写入 IndexedDB |
| 📋 LogPanel | `kernel:memory-updated` | 记录记忆变更日志 |
| 📦 Output 节点 | `kernel:memory-updated` | 根据当前记忆更新输出内容 |

### 11.3 用户修改数据的唯一路径

用户在 Graph/画布上想修改数据（如删除连线、新增节点）：
```
用户操作 → Graph 节点 → EventBus.emit('user:request-edit', { ... })
  → ⚙️ Kernel 接收 → 处理（验证/写入 Layer 2）
  → 重新走「写回」流程
  → EventBus.emit('kernel:memory-updated', { ... })
  → Graph 节点收到 → 反映修改
```

**关键约束：Graph 节点绝不直接修改内核数据，所有修改必须经内核处理。**

### 11.4 内核边界红线一览

```
🚫 内核绝对不做的 5 件事：
  1. 不调用 LLM                          → 这是 🤖 LLM 节点的职责
  2. 不渲染图谱                         → 这是 🕸️ Graph 插件节点的职责
  3. 不持久化数据                       → 这是 🗄️ Storage 节点的职责
  4. 不做执行控制（开始/暂停/停止）       → 这是外部编排层的职责
  5. 不管理画布上的连线/节点位置         → 这是 Canvas 自身的职责

✅ 内核只做的 3 件事：
  1. 查记忆  → 检索洋葱层 + 注入上下文
  2. 验幻觉  → 提取三元组 + 冲突检测 + 决策
  3. 写回    → 写入 Layer 2 + 降级 + 发 EventBus 事件
```
